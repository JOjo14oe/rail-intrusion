# C3 跨序列泛化：换站/换线路后掉多少

来源类型：【消融】（见 `docs/report-conventions.md`）

一句话结论：同一份权重，从"同场景混切"的验证集换到**整条序列都没见过**的验证集，mAP50 从 **0.7348 掉到 0.6683**（−0.0665），mAP50-95 从 0.4721 掉到 0.3777（−0.0944）。掉的主要是**精确率**（0.7521→0.6665），也就是新场景带来了更多误检，而不是把目标全丢了（召回 0.6584→0.6601，基本没变）。

## 1. 为什么必须做这个对照

之前的 0.7027 / 0.7348 都在"同一场景内部按时间切分"的验证集上取得：训练集和验证集来自同一段视频、同一座车站、同一天光照。这种切分回答的是"在这条线路上能不能认出来"，**不能**回答"换一条线路还能不能用"。

C3 就是把这个坑显式化：**验证集里的每一帧，都来自训练时一帧都没出现过的序列**。

## 2. 切分怎么做的

工具：`tools/build_osdar23_yolo.py --holdout-seqs ...`

`--holdout-seqs` 与旧的 `--val-seqs` 语义不同：

| 参数 | 语义 | 会不会泄场景 |
|---|---|---|
| `--val-seqs` | 这些序列**可以**产生 val，但它们前 70% 仍进 train | 会（同站同时段进两边） |
| `--holdout-seqs` | 这些序列**整条只进 val**，一帧都不进 train | 不会 |

留出的 9 条整序列，覆盖两类上线风险：

| 留出序列 | 帧数 | 场景类型 |
|---|---|---|
| `14_signals_station_14.1/14.2/14.3` | 30 | 未见过车站 A（信号机密集） |
| `9_station_ruebenkamp_9.1…9.5` | 50 | 未见过车站 B（有站台行人） |
| `12_vegetation_steady_12.1` | 98 | 未见过区间正线（植被） |

构建结果（`data/osdar23_yolo43_c3/stats.json` + 目录实测）：

- `train 1336 / val 178`，类别固定 5 类（`buffer_stop, catenary_pole, person, road_vehicle, signal_pole`），与 A 轴同一套类别编号
- val 目录里的序列名**只有**上面 9 条，已逐条核对
- 数据目录已进 `.gitignore`

> 复盘：第一次构建时脚本**没有清空** `images/` 与 `labels/`，导致上一版（`21_station_wedel`）的 340 帧残留在新 val 里，val 变成 478 帧的两套切分混合物。已给构建脚本加上落盘前 `shutil.rmtree(images/labels)`，第二次构建才得到干净的 178 帧。

## 3. 结果

权重：`runs/detect/osdar23-yolov8n-1359img-1280/weights/best.pt`（A 轴那次，60 epoch，imgsz 1280，batch 4）
评测：`python -u tools/verify_per_class.py <权重> 1280 data/osdar23_yolo43_c3/dataset.yaml out/c3/c3_metrics.json`

| 验证集 | 帧数 | mAP50 | mAP50-95 | P | R |
|---|---|---|---|---|---|
| 同场景混切（A 轴） | 155 | **0.7348** | **0.4721** | 0.7521 | 0.6584 |
| 整序列留出（C3） | 178 | **0.6683** | **0.3777** | 0.6665 | 0.6601 |
| 差值 | — | −0.0665 | −0.0944 | −0.0856 | +0.0017 |

每类对照（mAP50 / mAP50-95）：

| 类别 | 同场景混切 | 整序列留出 | 差值(mAP50) |
|---|---|---|---|
| buffer_stop | 0.879 / 0.608 | **0.995 / 0.786** | +0.116（见下方警告） |
| catenary_pole | 0.610 / 0.300 | **0.753 / 0.425** | +0.143 |
| person | 0.742 / 0.421 | **0.574 / 0.232** | −0.168 |
| road_vehicle | 0.964 / 0.728 | **0.647 / 0.277** | −0.317 |
| signal_pole | 0.479 / 0.304 | **0.373 / 0.168** | −0.106 |

**必须写进材料的警告**：`buffer_stop` 在 C3 验证集里只有 **7 个实例**，0.995 是"几个框碰对了"的产物，不足以下任何结论。别引这个数。

## 4. 怎么读这张表（诚实版）

1. **总体确实退化，但幅度不大**：−0.067 mAP50。说"跨线路还是能用"过头，说"完全不能用"也不对。合理的说法是"换到未见过的车站，mAP50 掉约 7 个点"。
2. **退化集中在 person 与 road_vehicle**：这两个类在留出车站里的姿态、尺度、背景与训练车站差别最大（站台上的行人有蹲/侧身/被栏杆部分遮挡）。误检变多（P 掉 0.086），而不是漏检变多（R 几乎不变）。
3. **catenary_pole 反而升了**，属于**样本偏置**，不是能力提升：留出的 14.x / 9.x 里接触网杆又大又多（这类杆在画面里成排出现），比混切验证集里的杆更容易。凡是"换个验证集某类就涨了"的情况，先怀疑验证集本身，而不是模型。
4. **不能与 0.7027 直接比较**：0.7027 是 516 图权重的数，本表用的是 1359 图权重；两者只能成对注明。
5. **单次训练、单种子**：本表不含训练抖动（实测抖动可达 0.04），所以 −0.0665 里有多少是"真退化"、多少是"这次训练刚好偏弱"，需要 G 轴三种子跑完后才能完全分开。在 G 出来之前，这个数只能当**趋势**用。

## 5. 能写进答辩的三句话

- "我们不是只在一个验证集上报了 mAP50 = 0.73，而是把 9 条整序列完全留出，得到 0.67：**这就是跨站泛化的代价，掉约 7 个点**。"
- "掉的是精确率不是召回率：新车站主要带来误检，说明下一步该做的是**负样本与场景级误报抑制**，而不是继续刷数据集 mAP。"
- "跨站测试集上的弱项是 `person` 与 `road_vehicle`，这正好是侵限场景里最需要的那一类目标——所以 V1 的融合与误报抑制，优先级高于继续提升杆状部件的分数。"

## 6. 复现命令

```bash
# 构建（整序列留出，5 类固定）
python -u tools/build_osdar23_yolo.py --out data/osdar23_yolo43_c3 \
  --classes "buffer_stop,catenary_pole,person,road_vehicle,signal_pole" \
  --holdout-seqs "14_signals_station_14.1,14_signals_station_14.2,14_signals_station_14.3,9_station_ruebenkamp_9.1,9_station_ruebenkamp_9.2,9_station_ruebenkamp_9.3,9_station_ruebenkamp_9.4,9_station_ruebenkamp_9.5,12_vegetation_steady_12.1"

# 评测（同一份权重，只换 data）
python -u tools/verify_per_class.py runs/detect/osdar23-yolov8n-1359img-1280/weights/best.pt 1280 data/osdar23_yolo43_c3/dataset.yaml out/c3/c3_metrics.json
```
