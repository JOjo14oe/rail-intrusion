# 车端侵限检测原型 · 技术报告 v1（激光雷达测距 + INS 测速）

> 本报告取代 `technical-report-v0.md`。v0 的距离来自单目透视标定、速度来自假设常数；
> 本版把这两项换成**传感器实测**，并逐项标注仍然成立的假设。

## 0. 一句话结论

在 OSDaR23 的实车数据上，管线可以对轨道区域内的行人给出**米级距离**（激光雷达）、
**实测接近速度**（INS 航向投影）与**四级报警**，端到端在单卡 RTX 4060 上 10 帧耗时 5.4 秒（含模型加载后 ≈2 fps@2464×1600）。
仍然不能被本数据验证的是：**"目标是否站在运行轨内"** 与 **"什么算一次侵限事件"**——43 个公开序列里没有这两项的真值。

## 1. 系统构成

```
多传感器序列（OSDaR23）
   rgb_center 2464×1600 ──┐
   lidar (6 线合并) ──────┤
   novatel_oem7_inspva ───┤
                          ▼
   ┌──────────────────────────────────────────────┐
   │ 1) 检测：YOLOv8n @1280，5 类，conf 0.35      │
   │ 2) 测距：点云投影到该相机 → 框底带上 20% 分位 │
   │ 3) 测速：INS north/east 按航向投影到车头方向  │
   │ 4) 风险：TTC = 前向距离 / 车速 → 四级 + 滞回  │
   │ 5) 输出：带框视频 + 事件 CSV                  │
   └──────────────────────────────────────────────┘
```

## 2. 关键公式

**测距（激光雷达）**

    点云 → 相机：p_parent = T_calib · p_lidar，p_opt = (-y, -z, x)
    图像：       u = fx·x/z + cx,  v = fy·y/z + cy
    目标深度：   取框底边往上 20% 带内的点，按深度取 20% 分位（近目标优先）

**测速（INS）**

    forward = north · cos(azimuth) + east · sin(azimuth)
    v_self  = |forward|

**风险**

    TTC = d_forward / v_self
    TTC > 8 s → notice ；≤ 8 → alert ；≤ 5 → warn ；≤ 3 → emerg
    升级当帧生效；降级需连续 5 帧确认（滞回）

## 3. 数据与硬件

| 项 | 值 |
|---|---|
| 数据 | OSDaR23（DZSF / Digitale Schiene Deutschland），序列 2_station_berliner_tor_2.1 等 |
| 传感器 | rgb_center 2464×1600、6 线合并点云、NovAtel OEM7 INS，硬件同步 10 Hz |
| 标注许可 | 标注 CC0 1.0；图像点云 CC BY-SA 3.0 DE（署名 DZSF 等四方） |
| 训练数据 | 18 个序列 / 516 张，train 361 / val 155，5 类 |
| 硬件 | RTX 4060 Laptop 8 GB、i9-13980HX、15.6 GB RAM、torch 2.14.1+cu130 |

检测模型在同一批 516 张上的验证指标（`docs/osdar23-yolo-training-report.md`）：
mAP50 0.7027、mAP50-95 0.4493；每类 mAP50：buffer_stop 0.813、catenary_pole 0.533、
person 0.729、road_vehicle 0.962、signal_pole 0.476。

**更新（43 个序列全解后）**：训练图 516 → 1359，同一 155 帧验证集上
mAP50 **0.7348**、mAP50-95 **0.4721**、R 0.6243 → 0.6584（`docs/accuracy-improvements.md` §1）。
本报告第 4 节的演示结果仍用 516 图权重跑出，**两者未串跑**，引用时必须成对注明数据规模。

**跨序列泛化（C3，自研）**：把 9 条整序列完全留出不参与训练（178 帧），同一 1359 图权重下降到
mAP50 **0.6683**、mAP50-95 **0.3777**、P 0.6665、R 0.6601；相对同场景混合切分的 0.7348 / 0.4721，
掉 **0.0665 / 0.0944**。退化集中在 person（0.742 → 0.574）与 road_vehicle（0.964 → 0.647），
catenary_pole 反升（0.610 → 0.753，属留出集的样本偏置而非模型变好）；buffer_stop 留出集只有 7 个实例，
其 0.995 不可引用。→ 引用规则：0.7348 是"同场景"读数，0.6683 是"跨站"读数，**不能互相冒充**
（`docs/c3-cross-sequence.md`）。

### 换掉"假设速度"后结论会变

同一段、同一模型、同一套距离，只换速度来源：

| 速度来源 | TTC 范围 | warn | emerg |
|---|---|---|---|
| 常数 15 km/h（常见做法：随手填） | 3.66 – 4.94 s | 10 帧 | **0 帧** |
| INS 实测 19.0 – 19.2 km/h | 2.90 – 3.86 s | 5 帧 | **5 帧** |

即：假设的速度能让"紧急"退化成"警告"，报警晚约 0.9 秒。这一格是"为什么必须接 INS"的直接证据，
也是"假设参数如何改变结论"的自证材料。

## 5. 已验证 / 未验证

| 项 | 状态 | 证据 |
|---|---|---|
| 点云↔图像几何 | **已验证** | 点云叠加在站台边缘线、栏杆、行人、楼宇窗格上，肉眼逐点吻合 |
| 距离是米级实测 | **已验证** | 由点云反投影，不再依赖画面上的人工标定 |
| 速度是实测 | **已验证** | INS 行内 north/east/azimuth，横向分量 ≈0 印证投影方向正确 |
| 检测指标 | **已验证（受限）** | 516 张、155 张验证集；不能当工业性能 |
| 目标是否在运行轨内 | **未验证（仍是假设）** | 用画面 ROI 梯形近似；尝试用点云拟合钢轨失败（下节） |
| 侵限事件定义 | **未验证（无真值）** | 43 个序列标注里没有"人站在运行轨内"这一项 |
| 可见光/红外融合 | **不成立** | 帧级融合与纯可见光逐帧相同；残差 424.7 px（`docs/c1-fusion-report.md`） |
| 时序对照 | **数据不足** | 段内无侵限场景，提前量指标无定义（`docs/c2-temporal-report.md`） |

### 用点云拟合钢轨（方案 D）失败

`railintrude/track.py` 用 `|z| < 0.15 m` 的近平面点 + 1.435 m 轨距分离左右轨，再做稳健拟合。
在 14_signals_station_14.1 上能沿弯道贴合真实钢轨；但在 2_station_berliner_tor_2.1 上**锁到相邻股道**，
走廊偏右约 3 m。根因：在这个高度层里站台立面、相邻股道、道床边缘与钢轨同高，钢轨不是最强结构，
且没有轨距之外的约束能确定是哪一对轨。**默认关闭**（`--gate-track` 为实验开关），因为启用会把
站台上的行人错判成"在轨"，把 5 帧 emerg 洗成 0 帧。

## 7. 必须写在材料里的话

1. 检测指标来自 516 张、155 张验证集，**是研究性质的数字，不是工业性能**。
2. "是否在轨"用画面 ROI 近似，**不是钢轨几何测量**；点云拟轨的尝试失败了。
3. 公开数据里没有"侵限事件"真值，所以本项目**不宣称**预警提前时间等事件级指标。
4. 融合（可见光+红外）在本数据上**没有**超过纯可见光，这是负面结论，不是没做。

## 8. 文献定位（与本项目结论的对应关系）

清单与逐篇解读见 `docs/literature-review.md`，原文与许可见 `refs/README.md`，BibTeX 见 `docs/refs.bib`。
本节的用途只有一个：**哪些结论能挂文献、哪些只能挂我们自己的实验**。

| 本报告的说法 | 文献能给什么 | 边界（必须自己扛的） |
|---|---|---|
| 公开铁路侵限数据少、评测协议不统一 | A1（T-ITS 2024 综述）、A2（TIM 2025 综述）指出研究不足与缺统一 benchmark | "43 个序列里没有事件真值"是我们逐序列数出来的，不是文献结论 |
| 融合的难点在**跨模态错配**，不在检测器 | B1（TPAMI 综述：data compatibility 是前置问题）、B2（ICCV'19 弱对齐/区域级对齐）、B3（TNNLS 弱对齐特征融合）、B4（MS-DETR 松耦合）、B5（T-IV 错配 benchmark） | "本项目融合失败是因为我们没做对齐"是我们自己的实测（几何残差中位 424.7 px、帧级融合与纯可见光逐帧相同），不能写成文献预言了我们的结果 |
| 下一版融合应改**区域级/松耦合**而不是逐像素 | B2、B4 给出了可实现的路线；B6（IJCAI'22 无监督错配配准）给出免配对训练的可能 | 我们尚未实现，属"未来工作"，不能写进结果 |
| 时序风险（TTC/提前量）比逐帧阈值更有意义 | C1（运动预测与风险评估综述：时间量纲的风险度量分类）、C3（CVPRW'25 铁路近失事件） | 我们**报不出**提前时间：段内无侵限事件 |
| "是否在轨"应当用几何判定 | D1（轨道区域）、D3（LiDAR 3D FOD）、D5（激光+相机联合） | 我们的 ROI 梯形是临时近似；点云拟轨尝试失败 |
| 加数据是当前最有效的提升手段 | 文献普遍认为数据规模是铁路视觉的瓶颈（A1/A2/A5） | "516→1359 图 mAP50 +0.032"是我们自己的单种子结果（`docs/accuracy-improvements.md`） |
| 跨域退化可量化、微调可恢复（C3） | E1（两阶段域适应）、E2（因果视角，未来工作） | 衰减幅度本项目已自测（0.7348 → 0.6683，留出 9 条整序列/178 帧）；"微调可恢复"仍未做 |

**不能写的话（无论文献怎么读）**

1. "我们的 mAP50 达到 SOTA" —— 无同协议可比对象。
2. "红外单独就能打"或"红外没用" —— 在 RGB 平面给红外打分得出的 0.1593 无效；有效观察只有"红外在自己像平面 640 下 mAP50 0.7674"。
3. 把 0.7027（516 图）与新模型 0.7348（1359 图）混着写 —— 两者是不同数据规模、同一 155 帧验证集，必须成对出现。
4. 把 0.7348 当成"实际线路精度" —— 那是同场景混切；真实跨站留出读数是 **0.6683**，差 0.0665，材料里必须给出后者。
